# xmip-core-transport-google-cloud-storage

Google Cloud Storage transport: the JSON API with a bearer token — list a prefix, get each object and delete it once the runtime accepts it, upload a Stream as an object — a bucket prefix is a Location. A technology of [xmip-core-transport](https://github.com/IlleNilsson/xmip-core-transport).

Requests go on connections kept between them (`http::endpoint::Connections`, offering HTTP/1.1): the transport holds them and hands them to every client it makes, so a call costs one exchange and not a connect, a TLS handshake and a `Connection: close`, as it did until 2026-09-27.

## One node receives an object

Several nodes may list one bucket; each object is received by one of them (ADR-0024, amendment 2026-11-20). A receive claims each object it hands over by uploading `<name>.xmip-claim` beside it with `ifGenerationMatch=0` (`Client::put_new`): "the request only proceeds if no object with the specified name exists in the bucket", and otherwise "fails with a status code of `412 Precondition Failed`" ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions), read 2026-11-20). The claim holds the claimed name the file family records, the object's name, the node's location and the time in nanoseconds; an object whose claim is listed is passed over without a request, and one whose upload Cloud Storage refuses is passed over. The sequence is the capability's, written once (`transport::listed::Claims`); this crate implements only the bucket's calls (`bucket::Bucket`, `transport::listed::Store`). The claim is deleted in the generation it was written in however the cycle ends — after the object on Accepted, alone on Refused and Failed — and one Cloud Storage does not answer is deleted at the next listing. A node that starts again (`Configured::on_node`) reads each claim listed at its first receive that reaches Cloud Storage and deletes every one its own name holds; another node's claim is left whatever its age, so a node gone for good leaves its objects claimed and in place. Per object the claim costs one conditional upload at the listing and one delete at its verdict, and the Location's token needs `storage.objects.create` for it. `Transport::claims` answers the same claim for one object by its address.

## How a received object is acknowledged

A receive deletes nothing and gets nothing: it lists the prefix, and each object's media `GET` is made when the runtime first reads its body (`transport::listed::Claims::listed`, the capability's one object-store receive, over `transport::body::fetched`), whole (`net::http` reads a response body whole), so a receive that lists a hundred objects holds none of them in memory. Every object stays in the bucket until the runtime gives its verdict after the whole receive cycle (runtime-model section 5). Accepted deletes the object. Refused leaves it where it lies — a refusal is not a consumption, and a Stream refused at a transport gate was never written to the Ledger, so the object is the only copy — and this Location does not receive it again while its `generation` is unchanged (`transport::Refused`, which the listing is sifted through: the client lists each object's `name` with its `generation`); one written again under its name is a new generation, and a new arrival. The memory is the node process's: a node started again receives a refused object once more, refuses it once more, and remembers it from then on. Failed leaves it, and the next receive lists and gets it again. Until 2026-10-02 a receive got every object it listed before handing any on. A crash before the verdict leaves the object too, claimed until its node starts again: at-least-once, never a loss. The delete is the one the receive made until 2026-10-02, so a verdict adds no request but its claim's delete.

The get and the delete are of the object as it was listed: each carries `ifGenerationMatch` with the generation the listing gave it (`transport::listed::AsListed`). One written again since the listing is answered `412 Precondition Failed`, and one deleted since `404 Not Found`: the get then reads nothing, so the cycle fails and the next listing takes the new generation as a new arrival, and the delete of an accepted object leaves the new generation where it lies. Until 2026-11-19 both were unconditional, so an object written again between the listing and the first read was read under the old generation, and one written again between the read and the acceptance was deleted unread. The generation and not the `etag`, on Google's advice: "You should generally use generation and metageneration preconditions instead of ETag preconditions" ([Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions), read 2026-11-19). The client's `put_new` uploads with `ifGenerationMatch=0`, which "only proceeds if no object with the specified name exists in the bucket" (the same page), `412` where one does, and hands back the generation it wrote: a receive claims with it, and the google-cloud-storage archive creates every object with it and never writes one over (ADR-0040).

A send target is read by `net::Target` in [xmip-core-library-net](https://github.com/IlleNilsson/xmip-core-library-net), the one reading of a URI every technology calls: scheme, authority, path and decoded query. Until 2026-09-28 it was read through the transport capability's `socket::target`, which split it on its first slash and left the query in the path.
